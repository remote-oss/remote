## 1. Why: the check never runs today (measured on this card's draft)

With the pinned VSCodium server 1.135.06055 (commit `1a46a584…`, `lib-product/test/fixtures/vscodium-reduced.json`):
1. **The launcher doesn't check.** `bin/codium-server` runs `"$ROOT/node" "$ROOT/out/server-main.js" "$@"` and
   nothing else.
2. **The check is a helper,** `bin/helpers/check-requirements.sh`. Its header says it "can exit with any of the
   following 2 exit codes and should be handled accordingly on the extension side. 0: All requirements are met, use
   the default server. 99: Unsupported OS, abort server startup with appropriate error message." It's `set -e`.
3. **In `ubuntu:18.04`** (glibc 2.27), the helper exits 99 and prints exactly F-0503 7.E1's two lines:

   ```
   Warning: Missing GLIBC >= 2.28! from /lib/x86_64-linux-gnu/libc-2.27.so
   Error: Missing required dependencies. Please refer to our FAQ https://aka.ms/vscode-remote/faq/old-linux for additional information.
   ```

   In `debian:12` it exits 0 and prints nothing.
4. **lib-server's own start script,** generated by `scriptFor({installMode: 'singleScript', step: 'start'}, …)` and
   run in `ubuntu:18.04` with the server installed as `bin/<commit>`, gave `status=ServerFailedToStart` with no
   `server.failure` fact, after the 15 s ready wait. The server alone exits 1 with node's loader error
   (`/srv/node: /lib/x86_64-linux-gnu/libc.so.6: version 'GLIBC_2.28' not found`). The start body's branch
   `[ "$EXIT_CODE" != 207 ] || leave LinuxPrereqs` never fires with this server.

5. **The Alpine server build** (`vscodium-reh-alpine-x64-1.135.06055.tar.gz`, the same commit) ships a byte-identical
   `bin/helpers/check-requirements.sh`. Run as `sh /srv/bin/helpers/check-requirements.sh` in `alpine:3.22` (pinned
   `sha256:5291449c…`), it **exits 0** and prints one line, `Warning: alpine distro detected, skipping GLIBCXX check`.
   It does the same with `libstdc++` added, which is the harness's dev container image (containers-09 §3.1). So every
   Alpine connect runs the helper and goes on, and gate row 1 isn't affected (athena on #904).

So today an old container gets the generic S034 dialog, never F-0503 7.E1's S346 with the check's text.
**remote-ssh is in the same position** (§5).

## 2. What this card builds

1. **A policy value `bundledHelper`.** The start body runs the server's helper before it launches the server.
   - **Exit 99** is `LinuxPrereqs`, with the helper's output as facts inside the result block.
   - **Exit 0, or any other code,** goes on to the launch.
2. **The remote-containers policy row** switches from `serverBundled` to `bundledHelper`. remote-ssh's and WSL's rows
   don't change, and the 207 branch stays (§5).
3. **lib-server's `prerequisitesMissing`** gains `detail: string`, read only from the facts inside the block (ADR-0010
   rule 1).
4. **C10** passes `detail` through unread as `requirementsNotMet`'s text (rule 4). C8 shows it as S346's detail.

## 3. The design

### 3.1 The policy (`policy/record.ts`, `policy/rows.ts`; transport contracts §5.0, amended in this PR)

- `RequirementsCheck` becomes `'none' | 'serverBundled' | 'serverBundledPlusAlpineProbe' | 'bundledHelper'`. JSDoc
  for the new value: "lib-server runs the server's `bin/helpers/check-requirements.sh` before each launch; exit 99
  aborts the start with the helper's output (F-0503 5.0 step 6, 7.E1)."
- `CONTAINERS_POLICY.requirementsCheck` is `'bundledHelper'`.
- **The contract row** for `requirementsCheck` in `docs/architecture/l3/transport-and-server/contracts.md` §5.0
  gains the value in its "values" cell, and the remote-containers cell becomes `bundledHelper` (F-0503 5.0 step 6;
  athena on #902). That edit is in this card's PR, for athena's design check.

### 3.2 The start body (`scripts/bootstrap.ts`, `startBody`)

- `StartParameters` gains `requirementsHelper: boolean`, with the JSDoc "Whether the server's own requirements helper
  runs before a launch (policy `bundledHelper`)". The parameter block gains
  `assignment('REQUIREMENTS_HELPER', yesNo(start.requirementsHelper))`.
- **Before the `nohup` launch line**, and only in the branch that launches, so never on reuse:

```sh
if [ "$REQUIREMENTS_HELPER" = yes ]; then
  REQUIREMENTS_SCRIPT=$INSTALL_DIR/bin/helpers/check-requirements.sh
  if [ -f "$REQUIREMENTS_SCRIPT" ]; then
    REQUIREMENTS_STATUS=0
    REQUIREMENTS_OUTPUT=$(sh "$REQUIREMENTS_SCRIPT" 2>&1) || REQUIREMENTS_STATUS=$?
    if [ "$REQUIREMENTS_STATUS" = 99 ]; then
      REQUIREMENTS_LINE=0
      if [ -n "$REQUIREMENTS_OUTPUT" ]; then
        while IFS= read -r REQUIREMENTS_TEXT; do
          [ "$REQUIREMENTS_LINE" -lt 20 ] || break
          REQUIREMENTS_LINE=$((REQUIREMENTS_LINE + 1))
          REQUIREMENTS_TEXT=$(printf '%s' "$REQUIREMENTS_TEXT" | tr -d '\r' | cut -c1-500)
          fact "server.prerequisites.$REQUIREMENTS_LINE" "$REQUIREMENTS_TEXT"
        done <<REQUIREMENTS_END
$REQUIREMENTS_OUTPUT
REQUIREMENTS_END
      fi
      leave LinuxPrereqs
    fi
  else
    fact server.prerequisitesHelper missing
  fi
fi
```

- **The `while` runs only when there's output** (triton on #904): a here-document of an empty value still holds one
  empty line, which would give `server.prerequisites.1=`. Checked in dash and bash with the guard: no output gives no
  fact, and `a\r\nb` gives `a` and `b`.
- **The `while` reads a here-document**, not a pipe. So it runs in the script's own shell, and `fact`'s
  `RESULT_FACTS` keeps what it adds, under BusyBox ash, dash and bash alike.
- **The helper runs through `sh`,** so a server tree on a `noexec` volume still runs it. Its stdout and stderr are
  taken together, the way it prints both lines (§1 item 3).
- **The 20-line and 500-character bounds** keep the block small. `cut -c` counts characters in a UTF-8 locale and
  bytes in `C`; either is a bound, and the rows use ASCII.
- **A missing helper** isn't a failure: the fact `server.prerequisitesHelper=missing` reaches C10's log (§3.4), and
  the launch goes on.
- Exit 0 or any other code: the launch goes on, and nothing of the output is kept.

`runtime.ts`'s `startOrReuse` takes the flag from the policy. Its parameter `allowedExtraOptions: readonly
ExtraStartOption[]` becomes `startPolicy: Pick<ServerPolicyRecord, 'allowedExtraStartOptions' | 'requirementsCheck'>`:
- `useHostProxy` and `fileWatcherPolling` read `startPolicy.allowedExtraStartOptions` as before;
- `requirementsHelper` is `startPolicy.requirementsCheck === 'bundledHelper'`.

remote-ssh's call (`pipeline/server-steps.ts:441` on main) passes `dependencies.policy` in place of
`dependencies.policy.allowedExtraStartOptions`, and containers-08's call does the same. That's the only remote-ssh
change, and its behaviour doesn't change: its row is `serverBundled`.

### 3.3 The failure's detail (`lifecycle/runtime.ts`)

- `StartFailure`'s `{kind: 'prerequisitesMissing'}` becomes `{kind: 'prerequisitesMissing'; detail: string}`.
- **On `LinuxPrereqs`:** `detail` is the facts `prerequisites.1`, `prerequisites.2`, … from `block.serverFacts`,
  taken in numeric order from 1 until the first missing one, and joined with `\n`. With none (exit 99 with no
  output, or remote-ssh's 207), it's `''`.
- A pure function, `prerequisiteDetail(serverFacts): string`, beside `causeOf`.
- remote-ssh's `pipeline/failure.ts` (`case 'prerequisitesMissing'`) ignores `detail`, unchanged in behaviour. Its
  rows that build the failure literal add `detail: ''`.

### 3.4 C10 (containers-08's `server-steps.ts` and `failures.ts`)

- §3.7 row 8's reason becomes `{text: failure.detail}`, passed unread (ADR-0010 rule 4). With `''`, containers-11's
  S346 dialog has an empty detail.
- **The aka.ms link in that text** is the server's own output, shown as the check prints it, not a link we author.
  ADR-0008 and R-29 cover what we write, so they aren't broken. C8's own "Learn More" (S218) still opens our README's
  Requirements section (containers-11 §3.6).
- When the start's facts hold `server.prerequisitesHelper=missing`, C10 logs at warn: `the server has no
  requirements helper; the container's requirements weren't checked`.
